# リプレイ容量の調査

現行version4の保存済み完走記録1件を読取専用で解析した。runtime・保存原本は変更していない。MBは10進表記。

## 実測

|項目|値|
|---|---:|
|ZSTD保存ファイル|41,676,998 bytes（41.7 MB / 39.7 MiB）|
|展開後Variant|294,060,888 bytes（294.1 MB）|
|フレーム|8,200（60Hz、記録長約136.7秒）|
|最後のゲーム計測時間|約134.0秒（入退場等と記録長は異なる）|
|変更ノードのスナップショット総数|650,989|
|音符のスナップショット|472,011件／221,279,124 bytes|
|移動床のスナップショット|71,433件／20,001,240 bytes|
|地形タイルのスナップショット|18件／61,884 bytes|

項目別bytesは各描画辞書をvar_to_bytesで個別直列化した合計であり、フレーム辞書・ID等の外側構造を含まない。音符の合計だけで展開後全体の約75.2%に相当する。ファイル展開サイズはメモリ使用量ではなく、メモリ上のDictionary/Arrayには別途管理コストがある。

## 原因

1. 入力記録ではなく、毎physics tickの描画状態を保存する方式。
2. ReplayStore.captureはノード辞書同士を比較し、一項目でも変わると辞書全体を追加する。プロパティ単位の差分ではない。
3. MusicNoteは_processでyawとshineを更新するため、表示位置が固定でも毎tick変更扱いになる。変更のたびに画像パス、シェーダーパス、矩形、固定座標、描画順等も再記録される。
4. _collectはis_visible_in_treeだけを判定し、カメラ範囲を判定しない。画面外の音符・移動床・アニメーションも対象となる。
5. 辞書の文字列キー、パス、型情報と全精度の数値を繰り返す。ZSTD圧縮は有効だが、変化する多数の数値・辞書を相殺するには至らない。

画像・音声本体を毎回埋め込んでいるわけではない。画像はres://パス、音声はcueとして記録する。地形全体の毎tick保存も今回の主因ではない。ファイルは最新完走1件であり、複数プレイの追記蓄積でもない。

## 圧縮後の影響比較

原本を読み、メモリ上の各frame.changedからtexture=music_note.pngの項目だけを削除して、別の/tmpファイルへ同じstore_var/ZSTD方式で保存した。

- 原本：41,676,998 bytes
- 音符スナップショットを除外した比較用ファイル：13,855,846 bytes
- 差：27,821,152 bytes（約66.8%減）

これは容量寄与を確かめる実験で、音符描画を欠くため製品の軽量化実装・再生同等性の証明ではない。原本を置換していない。解析結果は/tmp/replay-size-audit/{result,compare}.json、実行スクリプトも同ディレクトリに置いた。

## 改善の優先順位

まず固定プロパティと変動プロパティを分け、更新では変化したプロパティだけを保存する。音符のshine/yaw等の装飾は初期位相と再生時刻から復元すれば、毎tick保存自体を減らせるが、現在の実表示スナップショット方式との再現性を検証する必要がある。次にアセットパス・シェーダー・ノード識別子を共通テーブル化する。カメラ外記録を省く案は再入場時の完全状態復元が必要。

プレイヤー・箱・ガムの物理的な動きは描画スナップショットで再現する方針を維持できる。入力から物理演算をやり直す方式への変更は本件に必須ではない。
