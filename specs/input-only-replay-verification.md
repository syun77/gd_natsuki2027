# 入力のみを保存するリプレイの検証

## 結論

今回のmacOS上の試験では、固定60Hzの入力列からプレイヤー・箱・ガムの観測した物理状態、得点、残機を再現できた。入力方式は容量削減の有力候補。ただしランダム粒子と描画時間依存の装飾は完全一致せず、Windowsを含む環境横断・コース完走全体の同一性を保証した試験ではない。

ゲーム本体、リプレイ保存形式、保存済み原本は変更していない。検証のみを実施した。

## 方法

`/tmp/input-replay-audit` に別のGodotプロジェクトを作り、既存シーン・スクリプト・アセットを参照した。通常のReplayStoreだけ検証用stubへ差し替え、背景リプレイ読込・描画記録・保存を停止した。物理演算やゲームルールは既存Game/Player/Gum/RigidBodyを使用した。

8アクション（左右移動、上下左右照準、ジャンプ、ガム）の強度をphysics tick前に与え、各tickにつきfloat32×8個を保存。移動には0.35/0.65のアナログ強度も使用。別プロセスで同じ初期状態を作り、保存した入力列だけを与えた。比較用の状態JSONは観測専用で、再生時の補正・座標注入には使わない。

試験用入力列は規則的に移動・ジャンプ・発射・弛緩・切断を繰り返す合成入力。既存41.7MBの人間のプレイを入力列へ変換したものではない（現行保存には元入力がない）。

観測は各physics tickのプレイヤー位置／速度／外部速度、4個の箱の位置／角度／速度、ガム接続有無／モード／経路長、ゲーム計測時間／得点／残機／シーン。浮動小数比較の許容差は1e-5、プレイヤー位置差は別途距離で集計した。描画は粒子データのhashと先頭音符のyawを比較し、画像全体の一致試験ではない。

## シナリオと結果

物理更新は全試験60Hz。Godot4.5.1で60fpsの基準記録を作り、別processで再生した。30/144fpsは `--fixed-fps` による描画/idle更新周期の変更で、実GPUの負荷試験ではない。

|シナリオ|記録長|再生条件|結果|
|---|---:|---|---|
|共有物理検証sceneの入口周辺|1800ticks/30秒|4.5.1、30/60/144fpsと4.7.2、60fps|全観測物理項目が許容差以内。プレイヤー位置差0px|
|実Time Attack sceneの入口周辺|1800ticks/30秒|4.5.1、30/60/144fps|同上|
|箱引き初期配置を使う共有scene|1800ticks/30秒|4.5.1、30/60/144fpsと4.7.2、60fps|同上。LightBoxがx360→約293.8へ動く引き寄せを含む|
|箱引き配置から長時間継続|8200ticks/約136.7秒|4.5.1、144fpsと4.7.2、60fps|同上。得点110、最終残機3、接続819ticksが一致。残機減少4回と増加4回を含む|

計13条件の再生比較。長時間試験の基準で残機減少は4回で、死亡/復帰・アイテム取得を含む。初期配置を一度設定した後は入力だけを与え、途中の座標補正や物理パラメーター変更はしていない。全コースの完走、ゴール結果画面、ポーズ／手動リトライ入力はこの試験の対象外。

## 容量

|記録長|入力列非圧縮|同じZSTD保存方式|
|---|---:|---:|
|1800ticks/30秒|57,612 bytes|1,321 bytes|
|8200ticks/約136.7秒|262,412 bytes|6,168 bytes|

float32×8action×tick数に小さなVariantヘッダが加わる構成。画像、描画状態、物理座標を含まない。合成入力が反復的なので圧縮率が高く、実際のパッド操作で同じ圧縮率になるとは限らない。ステージ/設定/バージョン等の識別情報、乱数seed、ポーズ/再起動等の追加入力を含む製品formatの最終容量でもない。

同じ長さだった既存41.7MBリプレイとの容量比較は、異なるプレイ内容による方式比較であり、同一プレイの等価変換ではない。非圧縮でも今回の入力列は約262KBに収まった。

## 一致しないもの・採用前の条件

- ショット粒子は内部RandomNumberGenerator.randomize()を使い、同じ入力・同じfpsでも乱数粒子データが変わった。長時間試験では約3770ticksが不一致。入力だけから同じ粒子を再現するにはseed等の初期条件も必要。
- 音符yawは_process(delta)で進む。60fps同士は一致したが、30/144fpsでは物理tickの観測時刻に差があり、長時間144fps比較で8147/8200ticksが不一致。完全な見た目の一致には固定tick時刻への統一等が必要。
- 現行は物理を動かさない描画再生だが、入力再生はゲームルール/物理を再実行する。取得・死亡・得点処理が実行されるため、通常のベスト記録・リプレイ保存を変更しない再生用制御が必要。試験ではstubで保存を遮断した。
- 同一のステージ、初期状態、調整値、物理tick rate、入力強度と押下/解放タイミングを揃える必要がある。物理状態・地形の更新後に旧入力を再生した結果は同一とは限らない。
- 同じMacで4.5.1→4.7.2が一致したのは今回の試験結果であり、任意のエンジン更新・CPU・OSでの決定性保証ではない。Windows実機、複雑な多剛体接触、コース全体を別途試験する必要がある。

## 再実行と成果物

一時プロジェクト内の `main.gd` / `probe.gd` / `sampler.gd` / `store_stub.gd` を使用。基準：

```
Godot --headless --path /tmp/input-replay-audit --log-file /tmp/input-replay-audit/run.log --fixed-fps 60 --script res://main.gd -- record60 rigidlong
```

同じ引数末尾を `replay144 rigidlong` にし `--fixed-fps 144` で入力再生。`record60` だけが入力tapeを作り、それ以外は既存tapeを読む。scenarioはfixture/stage/rigid/rigidlong。各記録と観測JSON、input .dat/.zst、比較結果comparison.jsonは同じ/tmp配下。集計は `python3 /tmp/input-replay-audit/compare.py`。
